# Building for iOS without a Mac

iOS apps can only be built on macOS with Xcode. This guide covers building
BBB Mobile on a cloud Mac and distributing it through TestFlight.

## Current state of iOS support

Read this first: **screen sharing is not implemented on iOS yet.**

| Part | iOS status |
|---|---|
| App shell, portal WebView, classes, camera, microphone | Expected to work (shared React Native code), not yet tested on a device |
| `modules/bbb-native` | Stub: only `getDefaultUserAgent()` exists (returns `null`) |
| Screen sharing | Not implemented. The web client shows the share button (the app identifies itself as `BigBlueButton-Tablet`), but the native calls are missing and sharing fails |

On iOS, screen capture outside the app requires a **ReplayKit Broadcast Upload
Extension**, a separate target that runs in its own process, shares data with the
app through an App Group, and is limited to about 50 MB of memory. The
[`bigbluebutton-tablet-sdk`](https://www.npmjs.com/package/bigbluebutton-tablet-sdk)
package contains such an implementation (`ios/`, `ios-common/` and
`ios-broadcast-upload-extension/`), which can serve as the starting point. Its
license is ambiguous (LGPL-3.0 in `package.json`, MIT in `LICENSE`); keep its
notices in any file taken from it.

Work needed before iOS screen sharing works:

1. Implement the `BbbNative` screen share functions in Swift
   (`modules/bbb-native/ios/`), with the same JS API as Android
   (`initializeScreenShare`, `createScreenShareOffer`, `setScreenShareRemoteSdp`,
   `addScreenShareRemoteIceCandidate`, `stopScreenShare` and the events in
   `modules/bbb-native/src/BbbNativeModule.ts`).
2. Add the Broadcast Upload Extension target, the App Group entitlement and the
   `RPSystemBroadcastPickerView` trigger through a config plugin, since `ios/`
   is generated by `expo prebuild` and must not be edited by hand.
3. Add to `app.config.ts`:
   - `ios.infoPlist.NSCameraUsageDescription` and `NSMicrophoneUsageDescription`
     (WKWebView needs them for the class camera and microphone),
   - `ios.infoPlist.UIBackgroundModes: ["audio"]` so audio continues in the
     background.

Until then an iOS build is useful for checking the rest of the app.

## Prerequisites

- An **Apple Developer Program** membership (paid yearly). TestFlight and App
  Store distribution are not possible without it.
- The bundle identifier from `brand.json` (`iosBundleIdentifier`, currently
  `io.github.cnosmn.bigbluebuttonmobile`) registered under Certificates, Identifiers &
  Profiles. Use a separate identifier for the broadcast extension, for example
  `io.github.cnosmn.bigbluebuttonmobile.broadcast`.
- An app record in **App Store Connect** with that bundle identifier.
- An **App Store Connect API key** (Users and Access → Integrations → App Store
  Connect API) with the *App Manager* role: issuer ID, key ID and the `.p8` file.
  Cloud builds use it to manage signing and to upload builds.
- `.env.local` values (`EXPO_PUBLIC_PORTAL_URL`) provided to the build as
  environment variables or secrets, because `.env.local` is not committed.

## Option A: EAS Build (recommended)

[EAS Build](https://docs.expo.dev/build/introduction/) is Expo's cloud build
service. It runs `expo prebuild`, installs pods, creates or reuses signing
credentials and builds on macOS machines. It has a free tier with a monthly
build quota and queue times.

```bash
npm install --global eas-cli      # or use: npx eas-cli@latest <command>
eas login
eas build:configure               # creates eas.json and links the project
```

Add a production profile to `eas.json` if `build:configure` did not:

```json
{
  "build": {
    "production": {
      "ios": { "resourceClass": "m-medium" },
      "env": { "EXPO_PUBLIC_PORTAL_URL": "https://your-portal.example.com" }
    }
  },
  "submit": {
    "production": {}
  }
}
```

The portal URL can also be stored as an EAS environment variable instead of in
`eas.json` (`eas env:create`).

Build and upload to TestFlight:

```bash
eas build --platform ios --profile production   # asks for Apple credentials the first time
eas submit --platform ios --latest              # uploads the build to App Store Connect
```

EAS asks to generate and store the distribution certificate and provisioning
profiles. Let it manage them unless you already have your own.

## Option B: GitHub Actions macOS runner

Everything runs in your repository's CI. Public repositories get macOS runner
minutes for free; private repositories use the paid minutes quota (macOS
minutes are billed at a higher rate than Linux).

Store these as repository secrets:

| Secret | Content |
|---|---|
| `PORTAL_URL` | Value for `EXPO_PUBLIC_PORTAL_URL` |
| `ASC_KEY_ID`, `ASC_ISSUER_ID` | App Store Connect API key identifiers |
| `ASC_KEY_P8_BASE64` | The `.p8` file, base64-encoded |
| `APPLE_TEAM_ID` | Your 10-character team ID |

Example workflow (`.github/workflows/ios.yml`); adapt the Xcode version to what
the runner image provides and what the current Expo SDK requires:

```yaml
name: iOS TestFlight
on: workflow_dispatch

jobs:
  build:
    runs-on: macos-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npx expo prebuild --platform ios --clean
        env:
          EXPO_PUBLIC_PORTAL_URL: ${{ secrets.PORTAL_URL }}
      - name: Write App Store Connect key
        run: |
          mkdir -p ~/private_keys
          echo "${{ secrets.ASC_KEY_P8_BASE64 }}" | base64 --decode \
            > ~/private_keys/AuthKey_${{ secrets.ASC_KEY_ID }}.p8
      - name: Archive
        env:
          EXPO_PUBLIC_PORTAL_URL: ${{ secrets.PORTAL_URL }}
        run: |
          xcodebuild -workspace ios/BBBMobile.xcworkspace -scheme BBBMobile \
            -configuration Release -destination 'generic/platform=iOS' \
            -archivePath build/BBBMobile.xcarchive archive \
            DEVELOPMENT_TEAM=${{ secrets.APPLE_TEAM_ID }} \
            -allowProvisioningUpdates \
            -authenticationKeyPath ~/private_keys/AuthKey_${{ secrets.ASC_KEY_ID }}.p8 \
            -authenticationKeyID ${{ secrets.ASC_KEY_ID }} \
            -authenticationKeyIssuerID ${{ secrets.ASC_ISSUER_ID }}
      - name: Export and upload to TestFlight
        run: |
          cat > ExportOptions.plist <<EOF
          <?xml version="1.0" encoding="UTF-8"?>
          <!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
          <plist version="1.0"><dict>
            <key>method</key><string>app-store-connect</string>
            <key>destination</key><string>upload</string>
            <key>teamID</key><string>${{ secrets.APPLE_TEAM_ID }}</string>
          </dict></plist>
          EOF
          xcodebuild -exportArchive -archivePath build/BBBMobile.xcarchive \
            -exportOptionsPlist ExportOptions.plist -exportPath build \
            -allowProvisioningUpdates \
            -authenticationKeyPath ~/private_keys/AuthKey_${{ secrets.ASC_KEY_ID }}.p8 \
            -authenticationKeyID ${{ secrets.ASC_KEY_ID }} \
            -authenticationKeyIssuerID ${{ secrets.ASC_ISSUER_ID }}
```

`expo prebuild` names the workspace and scheme after the app name in
`brand.json`; check the generated `ios/` directory in the job log if the names
differ. With `-allowProvisioningUpdates` and the API key, Xcode creates the
signing certificate and profiles automatically. Once the broadcast extension
exists, its bundle identifier and App Group must be registered as well.

## Option C: Codemagic

[Codemagic](https://codemagic.io) offers macOS build machines with a free monthly
quota and a UI for App Store Connect integration. Connect the repository, add the
App Store Connect API key under *Teams → Integrations*, and use a `codemagic.yaml`
that runs the same steps as Option B (`npm ci`, `npx expo prebuild --platform ios`,
then Codemagic's `xcode-project use-profiles`, `xcode-project build-ipa` and the
`app_store_connect` publishing step with `submit_to_testflight: true`).

## TestFlight

- After upload, App Store Connect processes the build (usually 10–30 minutes)
  and asks for export compliance; BBB Mobile only uses standard HTTPS/TLS and
  WebRTC encryption, which is exempt, so answer accordingly.
- **Internal testers** (up to 100 members of your App Store Connect team) can
  install it right away through the TestFlight app.
- **External testers** (up to 10,000, by email or public link) require a short
  Beta App Review for the first build of each version.
- TestFlight builds expire after 90 days.

Before each upload, increase `version` in `app.config.ts`; EAS can increment the
iOS build number automatically (`"autoIncrement": true` in the profile), while
with Xcode you set `ios.buildNumber` in `app.config.ts`.
